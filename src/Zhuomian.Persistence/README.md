# E3-2 Workspace Persistence

Independent .NET 9 module referencing only Core. [ADR-0009](../../docs/ADR/0009-workspace-persistence.md) is Proposed. No UI, launch call, resource inspection, deletion, telemetry or network access exists here.

`IWorkspaceStore` exposes synchronous bounded `Load`, `Save(Workspace)`, `Backup`, `Restore`. `WorkspaceFileStore.CreateDefault()` uses the current user's LocalApplicationData/Zhuomian/Workspace on fixed Windows NTFS. Root and fault injection are internal friend-test composition only; JSON cannot select either. Applications can inject an `IWorkspaceStore`. Operations take a process gate and an exclusive OS file handle on workspace.lock. Another process/instance receives Busy; callers decide when to retry.

`StorageResult` distinguishes committed, unchanged, not committed and unknown commit. If OS submission reports an error and a sharing/permission failure prevents readback, Unknown protects against falsely reporting no commit; callers must reload/retry the identical snapshot after the obstruction is gone. RecoveryResult contains the Workspace, structured error, primary error, recovery state, opaque evidence filename, quarantine evidence and read-only flag. Only explicit Restore changes disk after recovery; Load does not repair or initialize empty data. The lock/root may be created on Load, but no Workspace file is created. Enum-only `IStorageDiagnostics` reports no arbitrary text; exceptions never reach the sink. RawJson is a private recovery payload, explicitly excluded from diagnostics. Evidence files are local, contain private configuration and must never be uploaded automatically.

## Disk and compatibility

First disk `formatVersion=1`, domain `schemaVersion=Workspace.CurrentSchemaVersion=1`. They are separate counters. The envelope has formatVersion, uppercase SHA256 of the exact UTF-8 payload JSON, and payload. SHA256 detects accidental corruption, not authentic authorship; a user/account able to rewrite the file can recompute it. A real [v1 fixture](../../tests/Zhuomian.Persistence.Tests/Fixtures/workspace-v1.json) records four kinds, sharing, removed records, provenance, availability and asset references. Stable ID sorting of root collections gives deterministic writes; ItemIds preserve original order. There is no previously shipped disk format and no v0 migration.

Snapshot count/string/reference/UTF-16-validity preflight precedes DTO allocation; serialization writes through an 8 MiB bounded stream. The codec uses explicit DTOs and bounded System.Text.Json parsing, no runtime type deserialization. Duplicate JSON properties/structural IDs, forbidden execution/runtime fields and root corruption fail the whole document. Invalid single objects, conflicting identities and unknown kinds are quarantined; raw payload and dangling reference order remain recoverable. Unknown fields are retained in the original envelope on disk. Partial/unknown loads are read-only: Save, Backup and Restore refuse to discard them. No generic extension writer or placeholder Item is added to E1's closed Item family; consumers use Quarantine to show a future unsupported placeholder. Unknown/new domain or disk versions are explicit UnsupportedVersion and never automatically downgraded from a backup.

Budgets: 8 MiB/file, depth 32, string 32768 UTF-16 units, 64 object properties, 20000 array entries, 100000 total references, 10000 Item IDs, 1024 Space IDs, 128 KiB/object, 256 backups and 256 revision reservations, 64 MiB per recovery collection scan. Limit exhaustion returns TooLarge; no assets are cleaned to make room. Reservations/backup retention need an explicit ownership/export/cleanup decision before long-term daily use. No supported layouts, placement, appearance or global settings are fabricated; these future fields require reviewed DTO additions or a new format migration.

MigrationRegistry registers trusted pure consecutive steps starting at version 1, verifies bounded outputs and reapplication idempotence, and returns MigrationFailed/UnsupportedVersion without writing files. Current codec accepts only v1, so no historical migration runs. Synthetic 1→2 unit harnesses exercise framework rollback/failure/idempotence and are explicitly not released product history. Future real migrations must integrate into load with input/output fixtures and keep the source until explicit atomic promotion.

## Transactions and recovery

Every operation pins all observed Windows ancestors using non-reparse handles and rejects non-fixed/non-NTFS/aliased roots. Read/lock handles validate final DOS path, kind and single-link file identity. Directory handles deny write/delete sharing and are disposed at transaction end. Temp uses CreateNew, random owned basename, same directory, WriteThrough, Flush(true), bounded readback and checksum validation. Existing main commits via File.Replace; first creation via non-overwriting same-directory File.Move. No copy-overwrite fallback. A private fixed storage root and cooperating exclusive lock are required. Privileged/kernel attackers and hostile same-account concurrent namespace changes are not a supported security isolation boundary.

Before publishing, a complete immutable prepared-GUID.json reservation burns the revision/content pair. Lower revisions and same revision/different content are refused, including after failed replacement. Identical retries may proceed; canonical duplicate saves return Unchanged. Valid old main is archived first to a unique backup-GUID.json. The initial valid candidate is backed up before first publication, since there is no predecessor; failure may leave that initial candidate available for explicit recovery, without replacing prior user data. No backups are overwritten or removed. A failure before replacement preserves main; an error after successful replacement is checked against actual bytes under the lock and returned Committed. Diagnostic sink failure cannot undo or misreport a commit.

Load prefers valid main, otherwise selects the highest valid fully understood backup, ignoring corrupted backups, and returns BackupRecovered/read-only with the primary failure. It never promotes a partially decoded backup. Conflicting Workspace IDs fail closed. Restore atomically promotes a fully understood backup with revision above valid main, backup and reservation high-water marks; exact old main goes to a unique evidence-GUID.json, including corrupt bytes. Prepared records are not automatically loaded as user data. A corrupt reservation prevents mutation because its historic high-water mark is unknown. All backups, evidence, reservations, failed temp and source assets remain. No automatic garbage collection or TTL exists.

Flush(true)/WriteThrough request Windows cache/device flush; NTFS replacement supplies same-volume namespace atomicity under the tested API. .NET exposes no portable directory fsync, and this code does not claim directory metadata durability, guaranteed device cache honesty, or absolute power-loss protection. Actual Windows runner evidence and remaining Windows 11/device/power-loss gates are in [E3-2 evidence](../../docs/E3_2_PERSISTENCE_EVIDENCE.md).

## E3-3 lifecycle engineering API

WorkspaceFileStore also implements IStorageLifecycle. [Support/evidence](../../docs/E3_3_STORAGE_LIFECYCLE_EVIDENCE.md) and [Proposed ADR-0010](../../docs/ADR/0010-storage-lifecycle.md) define the conservative boundary. This changes no disk format, Save/Restore reservation semantics or launch permissions.

```csharp
var store = WorkspaceFileStore.CreateDefault(); // Windows fixed NTFS root only
StorageInventory inventory = store.Inventory();
RetentionPlan plan = store.DryRun();
StorageResult fresh = store.ValidatePlan(plan); // reacquires mutex; not a mutation lease
StorageResult refused = store.Apply(plan, explicitlyAuthorized: true); // MaintenanceDisabled
BackupExportPlan export = store.PlanBackupExport(); // validated source v1/schema1 + SHA256
StorageResult sourceStillFresh = store.ValidateExport(export);
StorageResult exportRefused = store.Export(export, explicitlyAuthorized: true); // MaintenanceDisabled
```

Inspect Error/IsComplete/TotalsComplete before using observed health. Entry IDs are random per scan, not filenames. Per-family remaining budget, aggregate inventory read budget, revision ranges and logical backup generations are redacted diagnostics; high-water revision never replaces prepared evidence. Unknown/unsafe/unreadable/corrupt/partial files block plans and remain untouched. Scan holds NTFS file handles and checks the namespace again; missing directories are never created, but the coordination lock may be created in an existing root.

Every entry has CanDelete=false and zero reclaim. Apply and external Export are unconditionally disabled and perform no filesystem calls; false authorization returns AuthorizationRequired. Plans are immutable and tied to one store instance, invalid after restart or any relevant state/identity change. No caller-supplied/configurable destination path exists. Export SHA256 is for explicit local review only, never logs/telemetry. No background maintenance, resource or managed-asset access, cloud upload or UI is added. **The 256-file quota is not relieved** and daily-use integration remains blocked on a proved retention/compaction/export policy.

## E3-4A history safety increment

[Proposed ADR-0011](../../docs/ADR/0011-safe-history-compaction.md) and [evidence](../../docs/E3_4_HISTORY_SAFETY_EVIDENCE.md) describe a shared content witness for main/backup/prepared, including contradictions at earlier revisions. Save/Backup/Restore refuse incomplete or contradictory history before mutation. Valid-main Load keeps a readable diagnostic Workspace but returns the history error and IsReadOnly=true when history is unsafe; consumers must check both fields, not just State. Canonical identical retry and stale-revision rejection remain. No new disk format, migration, archive movement or quota relief exists. All raw sources remain. Apply/Export stay disabled. Old-client executable counterexamples and 1000 real Save attempts deliberately retain the unresolved 256 limit and block a main-only migration design.
